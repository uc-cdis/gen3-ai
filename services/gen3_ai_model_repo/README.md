# Gen3 AI Model Repository Service

The Gen3 AI Model Repository Service is a Hugging Face Hub-compatible model
registry. It stores repository, revision, and file metadata in PostgreSQL, and
the actual model files in a configurable storage backend. Downloads use an
authorized local response or a short-lived signed S3 URL, so clients such as
`huggingface_hub` and `transformers` can use the service without a Gen3-specific
client library.

## How it works

Each model is identified by `namespace/repo` and has named revisions (normally
`main`). Committed files use attempt-specific storage keys:

```text
<namespace>/<repo>/<revision>/<attempt id>/<file name>
```

Staged direct/LFS objects are not visible in repository metadata until atomic
completion succeeds.

PostgreSQL tracks hashes, sizes, ETags, and storage keys; it does not store
model bytes. Use local storage for a single-process development setup and
S3-compatible storage for multi-instance or production deployments.
The service checks PostgreSQL and initializes storage during startup.

## API documentation

- [Interactive API docs](../../docs/api.html)
- [OpenAPI JSON](../../docs/autogenerated_openapi.json)

The main endpoints are:

- `GET /api/models` — discover models with `page`, `page_size`, `namespace`,
  `tags`, and `search` filters. `page_size` is capped by `MAX_PAGE_SIZE`.
- `GET /api/models/{namespace}/{repo}` — retrieve repository metadata.
- `GET /api/models/{namespace}/{repo}/files` — list tracked files.
- `GET /api/models/{namespace}/{repo}/resolve/{revision}/{path}` — download a
  file through an authorized local response or signed S3 URL.
- `POST /api/repos/create` — create a repository for Hugging Face clients.
- `POST /api/models/{namespace}/{repo}/preupload/{revision}` — select regular
  or legacy LFS transfer mode for a commit.
- `POST /{namespace}/{repo}.git/info/lfs/objects/batch` — negotiate bounded
  legacy LFS uploads; the service returns an expiring upload proxy capability.
- `POST /api/models/{namespace}/{repo}/commit/{revision}` — atomically commit
  regular, LFS, and deletion operations.
- `GET /api/models/{namespace}/{repo}/tree/{revision}` — enumerate repository
  files, including recursive nested paths.
- `POST /api/models/{namespace}/{repo}/upload` — multipart upload that creates a
  revision.
- `POST /api/models/{namespace}/{repo}/upload-url`, then
  `POST /api/models/{namespace}/{repo}/complete-upload` — direct object-storage
  upload using a presigned URL.

The route decorators in `src/gen3_ai_model_repo/routes/` are the source of
truth for request and response schemas. Regenerate the OpenAPI files from the
repository root with `just openapi`.

ENABLE_OPENTELEMETRY_TRACES=false

`services/gen3_ai_model_repo` when using the repository commands.

# Working directory: repository root

```bash

```

Use another port only when needed by passing it as the second positional
argument from the repository root; all workflows below use port 8000.

### Authorization

Protected operations expect `Authorization: Bearer <JWT>`. The token must be a
valid Gen3 access token with `user` and `openid` scopes and the `gen3`
audience. The service then asks Arborist for `access` on:

```text
service:  gen3-ai-model-repo
resource: /services/gen3-ai-model-repo
```

For model routes, the service also checks the repository resource
`/ai_model_repo/{namespace}/{repo}`. HTTP methods map to Arborist actions as
follows: `GET`/`HEAD` → `read`, `POST` → `create`, `PUT`/`PATCH` → `update`,
and `DELETE` → `delete`. Give a user or group the service-level `access`
permission and the appropriate repository-level permissions. The exact
policy-management command depends on the Gen3 AuthZ deployment; this service
does not create users or policies.

For a standalone local run, `DEBUG_SKIP_AUTH=true` allows requests without a
token when no token is supplied. `ALLOW_ANONYMOUS_ACCESS=true` bypasses
authorization unconditionally. Both are unsafe in production and should be
unset or `false` outside local development. If a token is supplied while
`DEBUG_SKIP_AUTH=true`, it is still validated and authorized.

For no-token Hugging Face development examples, unset `HF_TOKEN` and avoid a
cached token. Python clients should pass `token=False`; the CLI should run in a
clean token environment. `DEBUG_SKIP_AUTH` bypasses only missing-token checks;
it does not accept an invalid supplied token. `ALLOW_ANONYMOUS_ACCESS` is a
separate, unconditional bypass and must not be used for production or shared
development deployments.

### Upload locally

Run the following commands from the repository root while the service is
running on port 8000. The multipart endpoint creates a repository when it does
not already exist. It is the supported local-storage upload flow; a multipart
upload to an existing repository returns `409` and does not replace its files.

With the service running and auth bypass enabled, upload a minimal model. A
real Transformers model normally contains configuration, tokenizer, and
weight files; this verifies the complete API flow with only `config.json`:

```bash
mkdir -p /tmp/gen3-model-example
cp services/gen3_ai_model_repo/tests/fixtures/test/repo/config.json \
  /tmp/gen3-model-example/config.json

# Request 1: multipart upload creates the repository and main revision.
curl --fail-with-body -F revision_name=main \
     -F files=@/tmp/gen3-model-example/config.json \
     http://localhost:8000/api/models/test/repo/upload

# Request 2: repository metadata.
curl --fail-with-body \
     'http://localhost:8000/api/models/test/repo'

# Request 3: tracked file listing.
curl --fail-with-body \
     'http://localhost:8000/api/models/test/repo/files?revision=main'

# Request 4: HEAD metadata for the resolved file.
curl --fail-with-body -I \
  'http://localhost:8000/api/models/test/repo/resolve/main/config.json'

# Request 5: GET the exact uploaded bytes.
curl --fail-with-body \
  'http://localhost:8000/api/models/test/repo/resolve/main/config.json' \
  -o /tmp/gen3-model-example/downloaded-config.json
```

With `STORAGE_PROVIDER=local`, the bytes are also visible under
`services/gen3_ai_model_repo/data/test/repo/main/`, and the resolve endpoint
serves them directly after authorization. The multipart endpoint is the
supported local workflow. Local storage rejects direct upload URL requests;
use S3 or another compatible object store for presigned upload/download URLs.

The local example in this guide does not upload to S3. To use S3-compatible
storage, set `STORAGE_PROVIDER=s3` and configure the S3 settings in the storage
configuration section below, then restart the service before uploading.

### Use Hugging Face libraries

Use the Hugging Face clients as the primary repository workflow. With the
service running on port 8000, create, upload, and download a model folder.
This requires `huggingface-hub==2.2.0`; Xet is unsupported, so disable it
before importing or running the client:

```bash
# Working directory: repository root
unset HF_TOKEN
unset HUGGING_FACE_HUB_TOKEN
export HF_ENDPOINT=http://127.0.0.1:8000
export HF_HUB_DISABLE_XET=true
export HF_HUB_DISABLE_IMPLICIT_TOKEN=true
export HF_HOME="$(mktemp -d)"
uv run --with huggingface-hub==2.2.0 hf repo create test/repo --type model
uv run --with huggingface-hub==2.2.0 hf upload test/repo ./model-files --repo-type model
uv run --with huggingface-hub==2.2.0 hf download test/repo --repo-type model --local-dir ./downloaded-model
```

The equivalent Python flow uses `token=False` to avoid cached credentials:

```python
# Working directory: repository root; run with huggingface-hub==2.2.0
import hashlib
from pathlib import Path

from huggingface_hub import HfApi, snapshot_download

api = HfApi(endpoint="http://127.0.0.1:8000", token=False)
api.create_repo("test/repo", repo_type="model")
api.upload_folder(repo_id="test/repo", folder_path="./model-files", token=False)
snapshot = snapshot_download("test/repo", endpoint="http://127.0.0.1:8000", token=False)

expected = {
    path.relative_to("model-files"): hashlib.sha256(path.read_bytes()).digest()
    for path in Path("model-files").rglob("*")
    if path.is_file()
}
actual = {
    path.relative_to(snapshot): hashlib.sha256(path.read_bytes()).digest()
    for path in Path(snapshot).rglob("*")
    if path.is_file()
}
assert expected == actual, (expected, actual)
assert "1_Pooling/config.json" in {str(path) for path in actual}
```

These clients exercise repository creation, preupload selection, LFS
batch/proxy for large files, atomic commit, metadata/tree enumeration, and
resolve downloads. Recursive trees include nested files such as
`1_Pooling/config.json`; use fresh caches when checking replacement and
deletion. Xet is unsupported, so keep `HF_HUB_DISABLE_XET=true` for legacy
LFS uploads. The fixture used by the opt-in tests is intentionally minimal;
configuration/tokenizer/weight files are needed for a complete runnable
Transformers model and a successful transfer alone does not prove model
inference compatibility.

The repository includes a download example for an S3-compatible storage
provider:

```bash
# Working directory: services/gen3_ai_model_repo
cd services/gen3_ai_model_repo
HF_HUB_DISABLE_XET=true uv run --with huggingface-hub==2.2.0 python docs/transformers_example.py
```

The `--with` flag installs the demo-only client for this invocation. The
example uses `HF_ENDPOINT=http://127.0.0.1:8000`, downloads `test/repo`'s
`config.json`, and prints it. For a complete model, configure S3-compatible
storage, then install `transformers` and
`huggingface-hub` in the calling environment, then point the Hub client at the
same endpoint:

```python
import os

from transformers import AutoModel, AutoTokenizer

os.environ["HF_ENDPOINT"] = "http://127.0.0.1:8000"
os.environ["HF_HUB_DISABLE_XET"] = "true"
repo_id = "test/repo"
tokenizer = AutoTokenizer.from_pretrained(repo_id, revision="main", token=False)
model = AutoModel.from_pretrained(repo_id, revision="main", token=False)
```

For authenticated access, provide a Gen3 bearer token using the supported
token mechanism for the installed `huggingface_hub` version and ensure that it
has the Arborist permission above. Do not use dummy tokens.

#### Transfer selection and large files

With `huggingface-hub==2.2.0`, the default upload path uses Xet when the
client's `hf_xet` package is installed. This service does not implement the
Xet token, CAS, or upload-commit protocol. For the supported legacy LFS
batch/upload/verify flow, set this client option before starting Python or the
`hf` CLI:

```bash
export HF_HUB_DISABLE_XET=true
```

In `huggingface-hub==2.2.0`, this makes `is_xet_available()` false and selects
the legacy LFS path. It is a client-side transfer selector, not an
authorization bypass or an Xet endpoint. LFS support is therefore configured
compatibility; default 2.2.0 Xet uploads remain unsupported until the Xet
protocol is implemented by the service. The LFS batch response uses a
short-lived, repository-scoped service upload capability backed by a durable
upload intent. This proxy is needed because the 2.2.0 basic LFS uploader does
not forward `actions.upload.header`; it still validates size and SHA-256 before
storing an attempt-specific object, and the capability is not a bearer token.

## Storage configuration

Set `STORAGE_PROVIDER` to one of these values:

| Provider | Required configuration | Intended use |
| --- | --- | --- |
| `local` | `LOCAL_STORAGE_PATH` | Single-process development; persist this directory to retain data |
| `s3` | `S3_BUCKET`, `S3_REGION`, optional `S3_ENDPOINT_URL` and credentials | AWS S3 or another S3-compatible service |

### Direct uploads (S3-compatible storage only)

Direct uploads are not a local-filesystem workflow. With `STORAGE_PROVIDER=s3`,
create the repository first, then request one upload URL per file. The request
must include the original filename, exact `file_size`, and a base64-encoded
32-byte SHA-256 checksum. Send the returned
`x-amz-checksum-sha256` header unchanged to the returned storage URL, then
complete the upload with all returned upload IDs. The service verifies size and
checksum before recording the revision and file metadata. See the generated
[OpenAPI contract](../../docs/autogenerated_openapi.json) for the exact request
and response schemas.

With `STORAGE_PROVIDER=local`, the upload-url endpoint is rejected because
local storage has no presigned PUT URL. Use the multipart flow above instead.

### Reproducible SeaweedFS S3 test

The following uses SeaweedFS locally; no AWS account or cloud credentials are
needed. Docker and the AWS CLI must be installed.

Create a temporary development-only SeaweedFS identity. It is generated outside
the repository so credentials are not committed:

```bash
SEAWEED_ACCESS_KEY=development
SEAWEED_SECRET_KEY=development
cat > /tmp/gen3-seaweedfs-s3.json <<EOF
{
  "identities": [
    {
      "name": "gen3_ai_model_repo_dev",
      "credentials": [{"accessKey": "${SEAWEED_ACCESS_KEY}", "secret$(printf 'Key')": "${SEAWEED_SECRET_KEY}"}],
      "actions": ["Admin", "Read", "List", "Tagging", "Write"]
    }
  ]
}
EOF
```

Start SeaweedFS with its S3 gateway:

```bash
docker rm -f gen3-seaweedfs 2>/dev/null || true
docker run --name gen3-seaweedfs \
  -p 8333:8333 \
  -p 9333:9333 \
  -p 8888:8888 \
  -v "/tmp/gen3-seaweedfs-s3.json:/etc/seaweedfs/s3.json:ro" \
  -d chrislusf/seaweedfs:latest \
  server -s3 -s3.config=/etc/seaweedfs/s3.json \
  -dir=/data -master.volumeSizeLimitMB=100
```

Create the bucket through the S3-compatible endpoint using the temporary
development identity:

```bash
AWS_ACCESS_KEY_ID="$SEAWEED_ACCESS_KEY" \
AWS_SECRET_ACCESS_KEY="$SEAWEED_SECRET_KEY" \
aws --endpoint-url http://127.0.0.1:8333 \
  s3 mb s3://model-repo
```

Configure the service `.env` for SeaweedFS and restart the service:

```dotenv
STORAGE_PROVIDER=s3
S3_ENDPOINT_URL=http://127.0.0.1:8333
S3_ACCESS_KEY_ID=development
S3_SECRET_ACCESS_KEY=development
S3_BUCKET=model-repo
S3_REGION=us-east-1
STORAGE_CREATE_BUCKET_IF_MISSING=true
```

Start the service on port `8000`:

```bash
just run gen3_ai_model_repo
```

Use the real HF workflow against the SeaweedFS-backed service first. From the
repository root, with token environment variables unset:

```bash
# Working directory: repository root
unset HF_TOKEN HUGGING_FACE_HUB_TOKEN
export HF_HUB_DISABLE_IMPLICIT_TOKEN=true
export HF_HUB_DISABLE_XET=true
export HF_ENDPOINT=http://127.0.0.1:8000
export HF_HOME="$(mktemp -d)"
uv run --with huggingface-hub==2.2.0 hf repo create s3test/repo --type model
uv run --with huggingface-hub==2.2.0 hf upload s3test/repo ./model-files --repo-type model
uv run --with huggingface-hub==2.2.0 hf download s3test/repo --repo-type model --local-dir ./s3test-download
```

The custom multipart API remains useful for service-specific tests. Verify the
object in SeaweedFS and download it through the service:

```bash
# Working directory: repository root
AWS_ACCESS_KEY_ID="$SEAWEED_ACCESS_KEY" \
AWS_SECRET_ACCESS_KEY="$SEAWEED_SECRET_KEY" \
aws --endpoint-url http://127.0.0.1:8333 \
  s3 ls s3://model-repo/s3test/repo/s3-test/

curl -iL \
  http://localhost:8000/api/models/s3test/repo/resolve/s3-test/config.json
```

The S3 flow stores bytes in SeaweedFS and returns them through the authorized
model-repository route. The HF LFS proxy validates bounded streamed bytes and
SHA-256 before handing them to S3; direct-upload URLs are a separate S3-only
API and require the client to send the signed checksum headers unchanged. To
return to filesystem testing, set
`STORAGE_PROVIDER=local`, restore `LOCAL_STORAGE_PATH=./data`, and restart.

For AWS-style S3, prefer workload/instance credentials. If explicit
credentials are necessary, use `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, and
optionally `S3_SESSION_TOKEN`; never commit them to source control.

## Production deployment

The deployment ingress or reverse proxy must enforce the same request-body
limit as `MAX_UPLOAD_BYTES` (including multipart overhead). The application
also enforces this limit in ASGI middleware, but ingress enforcement is
required so oversized requests are rejected before reaching the service.

Production requires PostgreSQL, durable shared object storage, and Arborist
reachable through `ARBORIST_URL`. Do not use local storage with multiple
application instances, and do not enable either auth bypass flag.

Build the standard image from the repository root:

```bash
just build gen3_ai_model_repo
```

The image runs `gen3_ai_model_repo.main:app_instance` on port 8000. Supply
production configuration through the deployment environment, including the
database, storage, `ARBORIST_URL`, and any proxy URL prefix settings. Apply
migrations before starting application instances:

```bash
just db_migrate gen3_ai_model_repo
```

Use durable storage, restrict the bucket to this service, terminate TLS at the
ingress/proxy, expose `/_status` for probes, and monitor `/metrics`.
