# Gen3 AI Model Repository Service

The Gen3 AI Model Repository Service is a Hugging Face Hub-compatible model
registry. It stores repository, revision, and file metadata in PostgreSQL, and
the actual model files in a configurable storage backend. Downloads use an
authorized local response or a short-lived signed S3 URL, so clients such as
`huggingface_hub` and `transformers` can use the service without a Gen3-specific
client library.

## How it works

Each model is identified by `namespace/repo` and has named revisions (normally
`main`). Files use this storage layout:

```text
<namespace>/<repo>/<revision>/<file name>
```

PostgreSQL tracks hashes, sizes, ETags, and storage keys; it does not store
model bytes. Use local storage for a single-process development setup and
S3-compatible storage for multi-instance or production deployments.
The service checks PostgreSQL and initializes storage during startup.

## API documentation

- [Interactive API docs](../docs/api.html)
- [OpenAPI JSON](./docs/autogenerated_openapi.json)

The main endpoints are:

- `GET /api/models` — discover models with `page`, `page_size`, `namespace`,
  `tags`, and `search` filters. `page_size` is capped by `MAX_PAGE_SIZE`.
- `GET /api/models/{namespace}/{repo}` — retrieve repository metadata.
- `GET /api/models/{namespace}/{repo}/files` — list tracked files.
- `GET /api/models/{namespace}/{repo}/resolve/{revision}/{path}` — download a
  file through an authorized local response or signed S3 URL.
- `POST /api/models/{namespace}/{repo}/upload` — multipart upload that creates a
  revision.
- `POST /api/models/{namespace}/{repo}/upload-url`, then
  `POST /api/models/{namespace}/{repo}/complete-upload` — direct object-storage
  upload using a presigned URL.

The route decorators in `src/gen3_ai_model_repo/routes/` are the source of
truth for request and response schemas. Regenerate the OpenAPI files from the
repository root with `just openapi`.

## Local development

### Prerequisites and configuration

Install `uv`, `just`, `dbmate`, and PostgreSQL. The repository helper checks
these tools:

```bash
just setup
```

Create `services/gen3_ai_model_repo/.env`. This is a complete standalone
example using filesystem storage:

```dotenv
PGHOST=127.0.0.1
# The example Docker command below publishes PostgreSQL on host port 5433.
# Use 5432 instead if no other PostgreSQL server is using that port.
PGPORT=5433
PGUSER=postgres
PGPASSWORD=postgres
PGDATABASE=gen3_ai_model_repo
PGPOOL_MIN_SIZE=1
PGPOOL_MAX_SIZE=5
MAX_UPLOAD_FILES=100
MAX_UPLOAD_BYTES=5368709120

STORAGE_PROVIDER=local
LOCAL_STORAGE_PATH=./data

# Development only; never use this in production.
DEBUG_SKIP_AUTH=true
ENABLE_METRICS=true
PROMETHEUS_MULTIPROC_DIR=/tmp/gen3-model-repo-metrics
ENABLE_OPENTELEMETRY_TRACES=false
```

The relative local storage path is resolved from
`services/gen3_ai_model_repo` when using the repository commands.

Start PostgreSQL for this example with:

```bash
docker run --name my-postgres-db \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=gen3_ai_model_repo \
  -p 5433:5432 \
  -d postgres
```

For a fresh database, create the database and load the complete current schema
with `db_setup` and `db_load`. For an existing database, use versioned
migrations with `db_migrate` instead of the fresh-database load workflow.

```bash
just db_setup gen3_ai_model_repo
just db_load gen3_ai_model_repo
just install gen3_ai_model_repo
just run gen3_ai_model_repo
```

For an existing database:

```bash
just db_migrate gen3_ai_model_repo
```

Verify that the migrated database is the same one configured for the service:

```bash
set -a
source services/gen3_ai_model_repo/.env
set +a
PGPASSWORD="$PGPASSWORD" psql \
  -h "$PGHOST" -p "$PGPORT" -U "$PGUSER" -d "$PGDATABASE" \
  -c "SELECT current_database(), current_user; SELECT to_regclass('public.models');"
```

The result must include `public.models`. If it is missing, check that
`PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, and `PGDATABASE` are identical for
the Docker/PostgreSQL server, `dbmate`, and the service. Do not run `db_load`
against an existing database; use `db_migrate` instead.

The service listens on `http://localhost:8000`:

```bash
curl http://localhost:8000/_status
open http://localhost:8000/docs  # macOS; open /docs manually elsewhere
```

Use another port by passing it as the second positional argument, for example
`just run gen3_ai_model_repo 4141`.

### Authorization

Protected operations expect `Authorization: Bearer <JWT>`. The token must be a
valid Gen3 access token with `user` and `openid` scopes and the `gen3`
audience. The service then asks Arborist for `access` on:

```text
service:  gen3-ai-model-repo
resource: /services/gen3-ai-model-repo
```

For model routes, the service also checks the repository resource
`/ai_model_repo/{namespace}/{repo}`. HTTP methods map to Arborist actions as
follows: `GET`/`HEAD` → `read`, `POST` → `create`, `PUT`/`PATCH` → `update`,
and `DELETE` → `delete`. Give a user or group the service-level `access`
permission and the appropriate repository-level permissions. The exact
policy-management command depends on the Gen3 AuthZ deployment; this service
does not create users or policies.

For a standalone local run, `DEBUG_SKIP_AUTH=true` allows requests without a
token when no token is supplied. `ALLOW_ANONYMOUS_ACCESS=true` bypasses
authorization unconditionally. Both are unsafe in production and should be
unset or `false` outside local development. If a token is supplied while
`DEBUG_SKIP_AUTH=true`, it is still validated and authorized.

### Upload locally

With the service running and auth bypass enabled, upload a minimal model. A
real Transformers model normally contains configuration, tokenizer, and
weight files; this verifies the complete API flow with only `config.json`:

```bash
mkdir -p /tmp/gen3-model-example
cp services/gen3_ai_model_repo/tests/fixtures/test/repo/config.json \
  /tmp/gen3-model-example/config.json

curl -F revision_name=main \
     -F files=@/tmp/gen3-model-example/config.json \
     http://localhost:8000/api/models/test/repo/upload

curl 'http://localhost:8000/api/models/test/repo/files?revision=main'
```

With `STORAGE_PROVIDER=local`, the bytes are also visible under
`services/gen3_ai_model_repo/data/test/repo/main/`, and the resolve endpoint
serves them directly after authorization. The multipart endpoint is the
supported local workflow. Local storage rejects direct upload URL requests;
use S3 or another compatible object store for presigned upload/download URLs.

The local example in this guide does not upload to S3. To use S3-compatible
storage, set `STORAGE_PROVIDER=s3` and configure the S3 settings in the storage
configuration section below, then restart the service before uploading.

### Use Hugging Face libraries

The repository includes a download example for an S3-compatible storage
provider:

```bash
cd services/gen3_ai_model_repo
uv run --with huggingface-hub python docs/transformers_example.py
```

The `--with` flag installs the demo-only client for this invocation. The
example uses `HF_ENDPOINT=http://127.0.0.1:8000`, downloads `test/repo`'s
`config.json`, and prints it. For a complete model, configure S3-compatible
storage, then install `transformers` and
`huggingface-hub` in the calling environment, then point the Hub client at the
same endpoint:

```python
import os

from transformers import AutoModel, AutoTokenizer

os.environ["HF_ENDPOINT"] = "http://127.0.0.1:8000"
repo_id = "test/repo"
tokenizer = AutoTokenizer.from_pretrained(repo_id, revision="main")
model = AutoModel.from_pretrained(repo_id, revision="main")
```

For authenticated access, provide a Gen3 bearer token using the supported
token mechanism for the installed `huggingface_hub` version (commonly
`HF_TOKEN`) and ensure that it has the Arborist permission above.

## Storage configuration

Set `STORAGE_PROVIDER` to one of these values:

| Provider | Required configuration | Intended use |
| --- | --- | --- |
| `local` | `LOCAL_STORAGE_PATH` | Single-process development; persist this directory to retain data |
| `s3` | `S3_BUCKET`, `S3_REGION`, optional `S3_ENDPOINT_URL` and credentials | AWS S3 or another S3-compatible service |

### Reproducible SeaweedFS S3 test

The following uses SeaweedFS locally; no AWS account or cloud credentials are
needed. Docker and the AWS CLI must be installed.

Create a temporary development-only SeaweedFS identity. It is generated outside
the repository so credentials are not committed:

```bash
SEAWEED_ACCESS_KEY=development
SEAWEED_SECRET_KEY=development
cat > /tmp/gen3-seaweedfs-s3.json <<EOF
{
  "identities": [
    {
      "name": "gen3_ai_model_repo_dev",
      "credentials": [{"accessKey": "${SEAWEED_ACCESS_KEY}", "secret$(printf 'Key')": "${SEAWEED_SECRET_KEY}"}],
      "actions": ["Admin", "Read", "List", "Tagging", "Write"]
    }
  ]
}
EOF
```

Start SeaweedFS with its S3 gateway:

```bash
docker rm -f gen3-seaweedfs 2>/dev/null || true
docker run --name gen3-seaweedfs \
  -p 8333:8333 \
  -p 9333:9333 \
  -p 8888:8888 \
  -v "/tmp/gen3-seaweedfs-s3.json:/etc/seaweedfs/s3.json:ro" \
  -d chrislusf/seaweedfs:latest \
  server -s3 -s3.config=/etc/seaweedfs/s3.json \
  -dir=/data -master.volumeSizeLimitMB=100
```

Create the bucket through the S3-compatible endpoint using the temporary
development identity:

```bash
AWS_ACCESS_KEY_ID="$SEAWEED_ACCESS_KEY" \
AWS_SECRET_ACCESS_KEY="$SEAWEED_SECRET_KEY" \
aws --endpoint-url http://127.0.0.1:8333 \
  s3 mb s3://model-repo
```

Configure the service `.env` for SeaweedFS and restart the service:

```dotenv
STORAGE_PROVIDER=s3
S3_ENDPOINT_URL=http://127.0.0.1:8333
S3_ACCESS_KEY_ID=development
S3_SECRET_ACCESS_KEY=development
S3_BUCKET=model-repo
S3_REGION=us-east-1
STORAGE_CREATE_BUCKET_IF_MISSING=true
```

Start the service on port `8001` for this example (use `8000` if it is free):

```bash
just run gen3_ai_model_repo 8001
```

Then use the documented multipart upload command. Verify the object in
SeaweedFS and download it through the service:

```bash
AWS_ACCESS_KEY_ID="$SEAWEED_ACCESS_KEY" \
AWS_SECRET_ACCESS_KEY="$SEAWEED_SECRET_KEY" \
aws --endpoint-url http://127.0.0.1:8333 \
  s3 ls s3://model-repo/s3test/repo/s3-test/

curl -iL \
  http://localhost:8000/api/models/s3test/repo/resolve/s3-test/config.json
```

The S3 flow stores bytes in SeaweedFS and returns them through the authorized
model-repository route. To return to filesystem testing, set
`STORAGE_PROVIDER=local`, restore `LOCAL_STORAGE_PATH=./data`, and restart.

For AWS-style S3, prefer workload/instance credentials. If explicit
credentials are necessary, use `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, and
optionally `S3_SESSION_TOKEN`; never commit them to source control.

## Production deployment

Production requires PostgreSQL, durable shared object storage, and Arborist
reachable through `ARBORIST_URL`. Do not use local storage with multiple
application instances, and do not enable either auth bypass flag.

Build the standard image from the repository root:

```bash
just build gen3_ai_model_repo
```

The image runs `gen3_ai_model_repo.main:app_instance` on port 8000. Supply
production configuration through the deployment environment, including the
database, storage, `ARBORIST_URL`, and any proxy URL prefix settings. Apply
migrations before starting application instances:

```bash
just db_migrate gen3_ai_model_repo
```

Use durable storage, restrict the bucket to this service, terminate TLS at the
ingress/proxy, expose `/_status` for probes, and monitor `/metrics`.

## Tests and maintenance

```bash
just test gen3_ai_model_repo
just openapi
```

PostgreSQL/object-storage end-to-end tests are opt-in: set
`RUN_MODEL_REPO_INTEGRATION_TESTS=1` and provide live PostgreSQL plus the
storage provider configured in the environment before running the suite.
